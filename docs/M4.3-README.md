# M4.3 — Portable archive and cold-history storage

M4.3 keeps the relational database as hot storage while adding a portable, slower filesystem tier for immutable historical data. The initial rollout deliberately **does not delete hot rows**. Archive generation, verification, restore and hot+cold reads must prove themselves before pruning is considered.

## Portable format

Ticker history is written in monthly `.jsonl.gz` shards. Each shard has an adjacent `.manifest.json` containing the Trademinator portable format version, ticker schema version, exchange/symbol/period identity, month coverage, row count, first/last logical keys, gzip data filename, SHA-256 and compressed size. Financial OHLCV values remain exact decimal strings; UUIDs remain canonical strings and timestamps remain integer milliseconds. SQL dumps are not the archive format.

Archive manifests contain enough metadata to rebuild `archive_catalog` after a database loss. The active catalog records logical type, market identity, period, coverage, row count, versions, path, checksum, compressed size and verification state.

## Safety model

A shard is only catalogued as verified after the gzip stream is closed, SHA-256 and size are checked, the file is reopened and decompressed, every record is validated, and row count plus first/last logical keys match the manifest. Failed archive creation does not modify source rows.

Hot+cold reads merge by the natural ticker key (`exchange + symbol + period + microtimestamp`). Identical overlap is accepted. Different values for the same key are an integrity error. Overlapping/gapped catalog ranges and failed verification are visible to the OWNER archive page and verification command.

Archives are **not backups**. Continue normal database and filesystem disaster-recovery backups.

## Feature checkpoints

`feature_checkpoints` stores a versioned, checksummed carry window produced by the M2 feature engine. When rebuilding from a later boundary, the feature builder may resume recursive EMA/Wilder state from a compatible checkpoint and reads the prior 30 days of raw hot/cold closes only for elapsed-time return anchors. Missing or invalid checkpoints fall back to replaying raw history.

## CLI

```bash
# Create one month (never prunes)
php artisan trademinator:archive-tickers kraken BTC/USD 1m 2026-01
php artisan trademinator:archive-tickers kraken BTC/USD 1m 2026-01 --dry-run

# Export every eligible complete month older than ARCHIVE_AFTER_DAYS
php artisan trademinator:archive-eligible-tickers
php artisan trademinator:archive-eligible-tickers --dry-run

# Verify / recover catalog
php artisan trademinator:archive-verify
php artisan trademinator:archive-verify tickers/kraken/BTC%2FUSD/1m/2026-01.manifest.json
php artisan trademinator:archive-rebuild-catalog

# Validate or restore one shard/range
php artisan trademinator:archive-restore tickers/kraken/BTC%2FUSD/1m/2026-01.manifest.json --validate-only
php artisan trademinator:archive-restore tickers/kraken/BTC%2FUSD/1m/2026-01.manifest.json --from=1767225600000 --to=1769903999999

# Database-independent portable package. Ordinary exports never include secrets.
php artisan trademinator:portable-export /secure/path/trademinator.jsonl.gz --dataset=tickers
php artisan trademinator:portable-import /secure/path/trademinator.jsonl.gz --validate-only
php artisan trademinator:portable-import /secure/path/trademinator.jsonl.gz
```

The daily scheduler runs `trademinator:archive-eligible-tickers` at 04:10 UTC using the shared scheduler lock. It only exports and verifies complete eligible months. There is no automatic archive pruning command in M4.3.

## OWNER administration

`/owner/archives` is protected by the existing authenticated, verified `server-owner` middleware. It lists catalog coverage/health and provides create, verify, catalog rebuild, range restore, portable export, and validate/import operations. Portable imports default to validate-only in the web UI.

## Deployment

M4.3 adds `archive_catalog` and `feature_checkpoints` migrations. Configure a shared filesystem path when application nodes share one archive tier:

```dotenv
ARCHIVE_ENABLED=true
ARCHIVE_PATH=/var/lib/trademinator/archive
ARCHIVE_GZIP_LEVEL=6
ARCHIVE_AFTER_DAYS=90
```

Then run:

```bash
php artisan migrate --force
php artisan optimize:clear
php artisan config:cache
php artisan schedule:list
```

The archive filesystem must be included in operational capacity monitoring and disaster-recovery backups even though the portable data itself is database-independent.
